## 요약

이번 예선은 가상 쇼핑몰의 운영 관계자들을 카카오톡으로 인터뷰해 지식을 수집하고, 그 지식을 활용해 고객 상담 AI 봇을 구축하는 과제였다. 다른 참가자들의 공유를 통해 전체 인터뷰 대상이 **10명**이라는 점을 알았지만, 내가 AI 도구를 활용해 실제로 찾아 대화한 사람은 **8명**이었다. 끝내 해금하지 못한 2명의 이름이 **조억만·홍보걸**이라는 사실은 대회가 끝난 뒤에야 알았다.

**핵심 교훈: AI에게 업무를 위임하는 데는 성공했지만, AI가 막히기 시작했을 때 전략 전환이 늦었다. 상담 에이전트 개발도 약 13시에야 병행하기 시작했고, 공개 테스트케이스 역시 실질적으로 한 세트만 검증해 개선·재검증의 반복을 충분히 수행하지 못했다.**

## 2. 잘했던 점: 사람 대신 AI가 인터뷰했다

처음부터 AI를 운용할 생각이 없었던 건 아니다. 실제로 세 번째 사람을 찾으면서 이 규모의 대화를 사람이 일일이 관리하는 것이 비효율적임을 판단했고 자동화로 전환했다. AI는 질문을 이어가며 추가 관계자를 해금했고, 그 결과 8명까지 진행됐다.

따라서 이번 경험을 “AI를 믿어서 실패했다”로 정리하는 것은 맞지 않다. **초기의 성공적 위임을 다음 단계의 전략적 관리로 연결하지 못한 것**이 문제였다.

자동화가 잘되니 사람의 지시는 점점 “계속해 줘”에 가까워졌다. 그러나 **12시경부터** 반복 거절과 이관이 보이면서 초기와 다른 유형의 문제임을 알아차렸다. AI를 더 오래 돌리는 것만으로 해결될 가능성이 낮아진 시점이었다.

## 3. 병목은 세 가지였다

### ① 카카오톡 I/O 처리량

Windows 카카오톡을 화면 중심으로 제어하는 과정에서 창 전환, 입력, 전송, 답변 확인 및 복사, 재시도에 시간이 들었다. 여러 AI 세션이 질문을 생각해도 실제 앱을 조작하는 실행기는 순차적으로 동작하는 경우가 많아 속도의 상한이 생겼다.

다음에는 우선순위를 이렇게 바꿀 것이다.

- **구조화된 UI 읽기 우선**: Windows UI Automation/Win32를 검증하고, 안 되면 Android ADB 접근성 제어를 대안으로 검증한다.
- **증분 수집**: 마지막으로 읽은 메시지 뒤의 새 내용만 확인한다. 기존 내용을 매번 다시 가져오지 않는다.
- **비동기 큐**: 상대방의 답변을 기다리는 동안 다른 사람에게 질문을 보낸다.
- **오발송 방지**: 대화방별 실행 잠금, 중복 전송 방지, 대기 중 연타 방지, 중단 스위치를 마련한다.
- **실측**: UI 조작시간·상대방 응답 대기시간·모델 판단시간을 분리해 측정한다.

Jev처럼 빠른 선택형 모델을 UI 판단에 도입하는 것도 검토할 수 있다. 다만 **알려진 버튼과 텍스트를 직접 읽고 조작할 수 있다면 굳이 매번 모델 판단을 거칠 필요는 없다.** Jev는 예외 상황의 다음 조작을 고르는 보조 수단으로 시험하고, 실제 개선 폭은 벤치마크로 검증할 예정이다.

### ② 질문 전략의 정체

카카오톡 프로필을 요청하면 관계자가 대답을 피하거나 다른 사람을 지목하는 일이 반복됐다. 그때 “왜 회피하는지”, “소개를 위해 필요한 조건이 있는지”를 따로 분석시켰어야 했다.

연락처를 곧장 요구하는 것과, 실제 고객 문제를 풀다가 적절한 담당자를 자연스럽게 소개받는 것은 다르다. 후자의 경우에는 역할·권한·동의 같은 절차가 존재할 수 있다.

더 나은 질문 예시는 다음과 같다.

> 이 고객이 조합원 할인 혜택을 실제로 이용한 사례는 누가 가장 잘 알고 있나요? 확인할 수 있는 기록이나 안내 절차가 있을까요?

> 이 문제를 ○○ 담당자에게 넘겨야 한다고 하셨는데, 인터뷰를 요청하기 전에 누구의 확인이나 동의가 필요한가요?

**교훈은 “마지막 2명 찾기를 포기했어야 한다”가 아니다. “같은 방법으로 계속 찾기 전에 찾는 방법을 바꿨어야 한다”이다.**

### ③ 상담 에이전트 개발과 테스트 시작이 늦었다

**약 13시경에서야** 기존 인터뷰와 별개로 고객 상담 에이전트 개발을 병행하기 시작했다. 이미 대회가 시작된 지 약 3시간이 지난 시점이었다. 인터뷰가 진행되는 동안 최소 기능 봇의 API 연결, 응답 형식, 지식 조회와 예외 처리까지 먼저 준비해뒀다면 남은 시간에 검증과 보완을 더 많이 할 수 있었을 것이다.

개발 이후 대회에서 공개한 테스트케이스도 돌려봤지만, **실질적으로는 한 세트만 실행**했다. 따라서 검증 결과를 바탕으로 요건을 세분화하고, 실패 유형을 수정한 뒤, 같은 케이스를 재실행해 개선을 확인하는 반복 과정이 부족했다.

다음 대회에서는 테스트케이스를 단순한 마지막 확인 수단이 아니라 **처음부터 개발을 이끄는 회귀 테스트**로 사용하려고 한다.

1. 초반에 공개 요구사항과 테스트케이스를 분야별로 분해한다(주문/환불/배송/이관/개인정보/응답 규격 등).
2. 최소 동작 봇을 빠르게 구축하고 가능한 한 일찍 첫 테스트를 돌린다.
3. 각 실패를 재현 가능한 케이스로 기록하고 원인별로 수정한다.
4. 수정한 뒤 기존 테스트를 **반드시 다시 실행**해 회귀 여부를 확인한다.
5. 인터뷰에서 새로운 근거가 들어오면 지식 반영과 해당 시나리오 재검증을 반복한다.

특히 **14시 20분경** 신규 관계자 탐색을 멈추고 발굴률을 올리는 쪽으로 전환했지만, 이미 남은 시간이 적었고 카카오톡 실행기 병목도 심했다. 이 사실은 단순히 “전환을 더 일찍 할 걸”이라는 후회를 넘어, **발굴·개발·테스트를 처음부터 병렬 파이프라인으로 실행했어야 했다**는 교훈으로 이어진다.

## 4. 합격자 회고와 비교해 얻은 교훈

다른 참가자의 [AI_TOP_100 예선 회고](https://claude.ai/artifact/M4SfSb7kfsL9f5mW3v32Qv)에 따르면, 해당 참가자는 **10명 전원 확보, 질문 542건, 평균 발굴률 56%, 약 50건의 자료**를 기록했다. 이는 해당 참가자의 자체 보고이며 공식 채점 점수와는 구분한다.

이 회고에서 눈여겨본 차이는 세 가지였다.

**첫째, 스크린샷보다 접근성 트리를 사용했다.** macOS 접근성 API와 Swift를 이용해 카카오톡 메시지 내용·시각·링크를 직접 읽었고, 이미 읽은 줄은 건너뛰면서 창 읽기 시간이 2~5초 수준까지 단축됐다고 한다. 속도를 만든 핵심은 더 큰 모델이 아니라 **I/O를 간결하게 만든 구조**였다.

**둘째, 병렬 인터뷰가 맥락을 끊을 수 있다는 점을 발견했다.** 관계자별 워커를 늘렸을 때 담당자에게 넘긴 문제의 후속 질문이 끊겼고, 다시 중앙 지휘자와 문제 단위 추적으로 돌아왔다고 한다. “질문을 많이 보낸다”보다 “한 문제를 해결될 때까지 따라간다”가 중요했다.

**셋째, 마지막 두 사람은 조건부로 해금했다.** 그 회고에서는 구체적인 회원 경험을 묻다가 조억만이라는 이름이 등장했고, 인터뷰 참여·연락처 제공 동의 절차를 확인한 뒤 채널을 받았다. 홍보걸 또한 홍보 목적과 소개 조건을 충족하며 발견됐다고 한다. 단순 연락처 수집이 아닌 **업무 맥락과 소개 절차를 이해하는 문제**였다는 점이 드러났다.

해당 참가자는 5분 단위로 인터뷰 기록→지식 정리→질문 큐 보충→봇 반영을 반복하고, 자료 간 충돌도 별도 관리했다고 기록했다. 내 다음 도전에 적용할 수 있는 좋은 구조다. 다만 회고를 읽고 결과를 알게 된 지금의 해석과, 당시 실제로 알 수 있었던 정보는 분리해야 한다.

## 5. 시야를 넓히면 문제를 푸는 도구 자체가 달라진다

합격자의 회고를 읽으며 가장 참신하다고 느낀 부분은 **macOS의 시각장애인 지원을 위한 접근성 기능을 카카오톡 자동화에 활용했다**는 점이었다.

일반적인 컴퓨터 자동화를 떠올리면 화면을 캡처해 OCR이나 비전 모델로 글자를 인식하고, 다음 버튼을 판단해 클릭하는 방식부터 생각하기 쉽다. 나 역시 카카오톡 제어를 해결하면서 별도 PC, Android Studio·ADB, 더 빠른 Computer Use 모델 같은 방향을 먼저 떠올렸다.

그런데 이 참가자는 다른 길을 선택했다. macOS에서 화면 읽기 프로그램인 VoiceOver 등을 지원하기 위해 제공하는 **접근성 트리(Accessibility API)** 를 활용한 것이다. 앱이 노출하는 텍스트·입력창·버튼·요소의 관계를 구조화된 정보로 받아 읽었다. 즉, **화면을 이미지로 다시 해석하는 것이 아니라 운영체제가 이미 알고 있는 UI 정보를 이용한 접근**이었다. 이 방식으로 메시지를 증분 수집하고 구현을 개선해, 회고에 따르면 대화창 읽기 시간이 **2~5초** 수준까지 줄었다. 이 수치는 전체 질문·답변 왕복시간이 아닌 **대화창 읽기 단계의 소요시간**이다.

가장 인상 깊은 건 단순한 속도 개선이 아니다. **문제의 해법을 찾는 탐색 범위가 달랐다는 것**이다.

- 나는 “AI가 화면을 더 빨리 보고 클릭하게 하려면?”이라는 관점에 주로 머물렀다.
- 그는 “굳이 화면을 이미지로 읽어야 하나? 운영체제가 제공하는 구조화된 정보를 직접 읽을 수 없나?”라는 다른 관점에서 접근했다.
- 그 결과 더 빠른 AI 모델을 고르는 문제가 아니라 **불필요한 이미지 해석 단계를 제거하는 문제**가 됐다.

이 경험을 통해 **생각의 다양성과 넓은 시야가 AI 활용 능력의 중요한 일부**라는 점을 느꼈다. AI에게 더 많은 일을 시키는 것도 중요하지만, 어떤 문제를 어떤 추상화 수준에서 해결할 것인지 넓게 탐색하는 태도가 그보다 더 큰 차이를 만들 수 있다.

다음에는 자동화가 느리거나 막힐 때 지금 쓰는 방법을 최적화하는 것만 묻지 않고, 다음과 같이 접근하고 싶다.

> “현재 방식 외에 완전히 다른 기술적 접근 3가지를 제시해 줘. 화면 캡처·OCR 없이 해결할 방법은 없는지, 운영체제나 앱이 이미 제공하는 구조화된 데이터는 없는지, 아예 문제를 다르게 정의할 수는 없는지 검토해 줘.”

물론 접근성 API가 모든 앱에서 동일하게 작동하는 것은 아니다. **macOS 카카오톡에서 효과가 있었다는 사례를 Windows 카카오톡에 그대로 적용할 수 있다고 단정할 수는 없다.** Windows UI Automation/Win32, Android ADB 등은 실제 앱의 요소 노출 수준을 먼저 검증해야 한다.

핵심은 특정 기술의 채택 여부보다 **처음 떠오른 해결책에 갇히지 않고, 서로 다른 분야의 기술을 문제에 연결하는 능력**을 키우겠다는 점이다.

## 6. 진짜 실수: 문제를 느꼈는데 분석 질문으로 만들지 않았다

약 12시경부터 나는 “답변을 회피하고 담당자를 넘기기만 한다”는 패턴을 인식하고 있었다. 그런데 그 관찰을 AI에게 분석 작업으로 넘기지 않았다. 그때 이런 지시가 필요했다.

> 현재 관계자 8명을 확보했으나 나머지 2명을 찾지 못하고 있다. 최근 대화에서 연락처 요청이 반복적으로 거절되거나 다른 담당자에게 넘겨진다. 모든 인터뷰 기록과 문서를 분석해 **왜 막히는지 가설 3개**, 가설별 **새로운 질문 전략**, 성공·실패 판단에 쓸 **관측 지표**를 정리해라. 지금까지의 질문을 단순 반복하지 말아라.

이것이 반드시 성공했을 것이라고 할 수는 없다. 하지만 “더 해 줘”를 “왜 막혔는지 분석해 바꿔 줘”로 전환할 기회를 만들었을 것이다.

더 나아가 사람이 문제를 발견할 때까지 기다리기보다, AI가 성과 정체를 스스로 감지해 전략 변경을 제안해야 한다.

## 7. 다음 대회의 설계: Strategy Watchdog

| 감지 조건 (초기 정책안) | 자동 대응 |
| --- | --- |
| 유사한 연락처 요청 3회 연속 거절 | 질문 방식 변경, 소개 조건 탐색 |
| 담당자 간 2회 이상 이관 반복 | 동일 문제 추적, 승인·동의 경로 확인 |
| 새 근거 없이 질문량만 증가 | 질문 효율 분석, 신규 가설 생성 |
| 15분간 신규 관계자·자료 확보 없음 | 전략 재평가 및 운영자에게 전환 제안 |
| 마감 임박 | 탐색·검증·제출에 남은 시간 재배분 |

수치는 최종 규칙이 아닌 리허설용 시작값이다. 새 전략으로 전환한 뒤 실제 신규 정보가 늘었는지 확인해 조정해야 한다.

운영 구조는 **질문 생성 AI → 관계자별 작업 큐 → 메신저 I/O 어댑터 → 증분 대화 기록 → 공용 지식 저장소 → 전략 감시자**로 분리한다. **별도 개발·테스트 파이프라인**에서는 초반부터 최소 기능의 상담 봇을 실행하고 요구사항별 테스트 → 실패 분석 → 수정 → 전체 회귀 테스트를 지속한다. 인터뷰가 끝날 때까지 개발과 검증을 기다리지 않는다.

## 8. 다음에는 반드시 측정할 것

- 8개 대화방 대상으로 100회 이상 송수신 실험: **오발송·중복 발송 0건**
- 대화방 전환·메시지 수집의 p50/p95 비교
- 답변 대기 중 다른 관계자 작업 처리 가능 여부
- 담당자 이관 후 같은 문제의 후속 질문이 이어지는 비율
- 질문당 새로 확보한 유효 정보·자료 수
- 전략 변경 전후 신규 정보 증가량
- 공개 테스트케이스 **반복 실행 횟수·요건별 통과율·회귀 실패 건수**
- 첫 동작 봇 배포 시점, 최초 TC 실행 시점, 테스트 → 수정 → 재검증 사이클 수
- 마감 전 최종 검증·제출과 자동 루틴 종료 확인

## 마무리

세 번째 관계자 이후 자동화로 전환한 판단은 맞았다. AI가 8명까지 관계자를 찾아낸 것도 성과였다. 그래서 이번 회고를 단순히 실패담이라고 부르고 싶지는 않다.

하지만 자동화가 잘 돌아간다는 사실과 **올바른 방향으로 돌아간다는 사실은 다르다.** 또한 인터뷰가 자동화됐다고 해서 상담 에이전트 개발과 반복 검증까지 저절로 진행되는 것은 아니다. **12시경의 질문 정체, 13시경의 개발 착수, 14시 20분경의 늦은 방향 전환**이 이 두 문제를 분명하게 보여준다.

> **AI에게 일을 맡기는 데 성공했다면, 다음 과제는 그 AI가 잘못된 방향으로 오래 달리지 않게 만드는 것이다.**

다음번에는 버튼을 더 빨리 누르는 AI뿐 아니라, *“현재 방법은 효과가 떨어집니다. 다른 전략으로 바꾸겠습니다”*라고 먼저 말하는 AI 오케스트레이터를 만들고 싶다. 그리고 **첫 번째로 떠오르는 기술에 매달리지 않고, 접근성 API처럼 다른 분야의 해법까지 살펴보는 넓은 시야**를 갖고 싶다.
